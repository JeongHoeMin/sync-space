프론트엔드와 백엔드 개발자가 즉시 실무에 투입될 수 있도록, 요구사항을 바탕으로 구체적인 기획안, 개발 계획, 그리고 DB 스키마를 정리해 드립니다.
프로젝트의 풀스택 언어는 TypeScript를 사용하여 타입 안정성을 극대화하며, 프론트엔드 코드는 sync-space-app 폴더에, 백엔드 코드는 sync-space-server 폴더에 분리하여 구현해야 합니다
.

--------------------------------------------------------------------------------
1. 프로젝트 개요 및 기획안 (SyncSpace)
SyncSpace는 단순한 화면 공유를 넘어, 공유된 화면 위에 실시간으로 그림을 그리며 소통할 수 있는 데스크톱 전용 몰입형 커뮤니케이션 툴입니다
.
타겟 유저: 원격 코드 리뷰나 디자인 수정을 진행하는 개발자/디자이너, 즉각적인 피드백이 필요한 온라인 튜터 및 학생
.
핵심 가치: WebRTC 데이터 채널을 통한 초저지연 양방향 판서, Electron 기반의 쾌적한 데스크톱 경험, LiveKit SFU를 활용한 비용 효율성
.

--------------------------------------------------------------------------------
2. 프론트엔드 개발 계획 (sync-space-app 폴더)
프론트엔드는 Electron, React, Tailwind CSS를 기반으로 개발합니다
. 브라우저 탭의 한계를 벗어난 독립적인 데스크톱 앱 경험을 제공하는 것이 핵심입니다
.
화면 공유 및 캡처:
Electron의 desktopCapturer API를 사용하여 데스크톱 전체 화면 또는 특정 애플리케이션 창을 선택해 WebRTC Video Track으로 추가하고 스트리밍합니다
.
인터랙티브 상호작용 (Canvas 오버레이):
발신자 (화면 공유자): Electron의 transparent(투명) 창 속성을 활용해 전체 화면 위에 투명한 Canvas 오버레이를 띄웁니다
. 평소에는 클릭 이벤트가 화면 뒤로 통과(Click-through)되도록 하고, 판서 모드 활성화 시에만 드로잉 이벤트를 캡처합니다
.
수신자 (시청자): 브라우저 DOM Canvas API를 활용해 전달받은 비디오 스트림 위에 HTML5 <canvas>를 겹쳐 띄웁니다
. 마우스 드래그를 통해 (x, y) 좌표 및 이벤트(시작, 이동, 끝)를 추출합니다
.
데이터 동기화 (WebRTC DataChannel):
추출된 좌표, 색상, 펜 굵기 등의 드로잉 데이터는 0.5초 이내의 초저지연 동기화를 위해 Socket.io가 아닌 WebRTC DataChannel을 통해 양방향으로 브로드캐스팅합니다
.

--------------------------------------------------------------------------------
3. 백엔드 개발 계획 (sync-space-server 폴더)
백엔드는 NestJS, Socket.io, Zod를 기반으로 구현하며, 미디어 서버로는 **LiveKit Server(오픈소스 SFU)**를 연동합니다
.
아키텍처 및 보안:
도메인 주도 설계(DDD) 관점을 차용한 헥사고널 아키텍처를 적용해 비즈니스 로직과 외부 인터페이스(WebRTC, DB)를 철저히 분리합니다
.
모든 API 페이로드 및 소켓 데이터는 서버 진입점에서 Zod 라이브러리를 통해 스키마를 검증하고 잘못된 요청을 차단합니다
.
통신 보안을 위해 모든 미디어 통신은 SRTP로 암호화합니다
.
기능별 통신 프로토콜 구현:
인증/유저: 이메일/비밀번호 기반의 회원가입 및 로그인을 REST API(NestJS)로 처리하고 JWT를 발급합니다
.
채널 및 채팅: 사용자의 채널(방) 입장/퇴장 관리, 고유 접속 링크 생성, 접속자 목록 갱신, 실시간 텍스트 채팅은 Socket.io를 통해 구현합니다
.
미디어 통신: 1개 채널 당 최소 10명의 동시 화상 통화가 지연 없이 처리되도록 LiveKit SDK를 활용해 마이크 및 웹캠 스트림을 활성화합니다
.
파일 전송: 드래그 앤 드롭으로 전송된 이미지/파일은 AWS S3에 직접 업로드한 후, 생성된 URL을 Socket.io를 통해 채팅창에 전송합니다
.
인프라 및 배포:
Oracle Cloud 인스턴스 위에서 API 서버, PostgreSQL DB, LiveKit Media 서버를 모두 Docker 및 Docker Compose를 이용해 컨테이너 단위로 패키징하여 단일 명령어로 배포 가능하도록 구성합니다
.

--------------------------------------------------------------------------------
4. 데이터베이스 스키마 설계 (PostgreSQL 기준)
기본 DB는 PostgreSQL을 사용하며, 파일은 AWS S3에 저장합니다
. 초저지연이 필요한 인터랙티브 판서 좌표 데이터는 WebRTC DataChannel을 통해 휘발성으로 브로드캐스팅되므로 DB 저장 대상에서 제외합니다
.
다음은 백엔드 개발자가 즉시 ORM(예: TypeORM, Prisma 등) 모델링에 사용할 수 있는 핵심 테이블 구조입니다.
1. users (사용자 테이블) 회원가입 및 세션 관리를 위한 사용자 정보입니다.
id (UUID, Primary Key)
email (VARCHAR, Unique, Not Null) - 로그인 계정
password_hash (VARCHAR, Not Null) - 암호화된 비밀번호
created_at (TIMESTAMP, Default Current)
updated_at (TIMESTAMP)
2. channels (채널/방 테이블) 음성/화상 및 화면 공유가 이루어지는 방 정보입니다.
id (UUID, Primary Key) - 고유 접속 링크 생성을 위해 사용
title (VARCHAR, Not Null) - 채널명
host_id (UUID, Foreign Key -> users.id) - 방장 ID
is_active (BOOLEAN, Default True)
created_at (TIMESTAMP, Default Current)
3. channel_participants (채널 참여자 테이블) 접속자 목록 실시간 갱신 및 다대다 매핑을 위한 테이블입니다.
id (UUID, Primary Key)
channel_id (UUID, Foreign Key -> channels.id)
user_id (UUID, Foreign Key -> users.id)
joined_at (TIMESTAMP, Default Current)
4. messages (채팅 및 파일 테이블) 텍스트 채팅 내역 및 S3에 업로드된 이미지 파일의 URL 이력을 저장합니다
.
id (UUID, Primary Key)
channel_id (UUID, Foreign Key -> channels.id)
sender_id (UUID, Foreign Key -> users.id)
message_type (ENUM: 'TEXT', 'IMAGE', 'FILE')
content (TEXT, Not Null) - 텍스트 내용 또는 AWS S3 URL
created_at (TIMESTAMP, Default Current)
위 명세에 따라 프론트엔드 개발자는 sync-space-app 폴더에서 Electron + React 세팅 및 화면 캡처/오버레이 UI를, 백엔드 개발자는 sync-space-server 폴더에서 NestJS + Docker Compose 세팅을 즉시 시작하시면 됩니다.
